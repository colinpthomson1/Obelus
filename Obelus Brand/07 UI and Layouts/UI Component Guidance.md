# UI Component Guidance

## Buttons

Use one primary action per region. Primary buttons use Evidence Blue with Cloud text. Secondary buttons use an Ink border or quiet surface. Tertiary actions are text links.

Every button needs default, hover, focus-visible, active, disabled, loading, error, and success behavior. Focus rings are 2 px Evidence Blue or Aqua on dark backgrounds with a 3 px offset.

## Claim highlight

A claim highlight is a text-level annotation, not a large warning box. Use a low-chroma status background, a short underline derived from the obelus stroke, and a written status label.

## Finding summary

The first view should answer:

1. What did Obelus find?
2. What qualification matters?
3. How fresh is the information?
4. Which sources support or conflict with it?

## Status badge

Status badges combine icon, label, and tested foreground/background colors. Do not display a percentage as a “truth score.” If confidence is useful, explain what it measures and show the source process.

## Source row

Each source row includes publisher, document or page title, publication date, retrieval time when relevant, and whether the source supports, conflicts with, or only contextualizes the claim.

## Live state

Live Aqua communicates listening and streaming. Always pair it with a visible “Live” or “Listening” label and a recording/consent indicator. Never use a blinking red dot as the default.

## Loading

Use Proof Pulse for compact checks, Transcript Scan beside active speech, Source Exchange during deeper research, Obelus Resolve for larger handoffs, and Progress Divide only when real progress is measurable.

## Empty state

Teach the first action: “Start a conversation to see checkable claims appear here.” Include privacy and recording expectations before activation.

## Error language

State what happened, why if known, and what to do next. Example: “The source could not be reached. Try this check again.” Do not blame the user or use humor in a failed fact-check.
